# QA hand-off: https://harbourline.example/

Task list for an implementing agent, generated by the qa-audit skill. The human report (`index.html`) has the same findings with charts and screenshots; ids match (BUG-01 = #1 there).

## Rules for the agent

- Work in the order below (severity, then ICE). One commit or PR per BUG id; put the id in the message.
- Never submit real forms, payments or messages on production, and never send test events into production analytics. Use the synthetic checks in `qa-tests/`.
- Tasks marked `owner: decision` need the site owner's answer first: ask, do not guess business facts (prices, terms, legal text, which language versions to keep).
- Tasks marked `owner: admin` happen in an admin UI (CMS, GTM, GA4, Search Console, hosting). If you have no access, prepare the exact change and hand it to a human.
- Status `hypothesis` means: reproduce first. If it does not reproduce, report that and skip the fix.
- A task is done only when its **Done when** line holds and its test passes. Then rerun the whole suite to catch regressions.

### BUG-01 · critical · mobile · observed

Title: Quote form is 690 px wide on a 390 px phone; last fields off-screen
Type: bug · ICE 648 (I9 C9 E8)
Where (url): https://harbourline.example/#quote
Where (selector): `.wpcf7 form`
Where (file): `theme/assets/css/forms.css`
Environment: Playwright Chromium and WebKit, 390 × 844, touch

Reproduce:
1. Open https://harbourline.example/ at 390 × 844 (iPhone 13/14 size).
2. Tap "Get a quote" to jump to #quote.
3. Try to reach the Phone and Email fields.

Expected: The form fits in one column; no sideways scroll.
Actual: The form grid has three fixed 220 px columns (690 px in total). The page scrolls sideways and Email sits off-screen.
Evidence:
- shot: Quote form at 390 px (outlined) (file: `shots/02-quote-form-390.jpg`)
- dom: documentElement.scrollWidth = 702 at innerWidth 390; form computed grid-template-columns: 220px 220px 220px

Fix:
1. In the theme CSS, change the form grid to repeat(auto-fit, minmax(14rem, 1fr)).
2. Set inputs to width: 100% and font-size: 16px to stop iOS zooming in.
3. Re-run T06, then check once on a real phone.

Suggested change:

```css
.wpcf7 form {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(14rem, 1fr));
  gap: 10px;
}
.wpcf7 input, .wpcf7 select, .wpcf7 textarea {
  width: 100%;
  font-size: 16px; /* stops iOS zoom */
}
```

Options considered:
- Hide the extra fields on phones: rejected, because sales need the route and the cargo type.
- A separate mobile form: rejected, because two forms to maintain would drift apart again.

Done when: T06 passes at 390 and 820 px, and no field needs a sideways scroll.
Test: `T06` (no_h_scroll) — No sideways scroll at 390 and 820 px. Run: `QA_ONLY=T06 npx playwright test`
Owner action: Agent can do it in code (theme, plugin code, templates, config in the repo)
Risk: Other forms on the site may share the class; check the contact page too.
Pre-mortem: It failed because the cache plugin kept serving the old CSS file. Purge the cache and bump the theme version in the same deploy.

### BUG-02 · critical · analytics · observed

Title: Form success event no longer sends generate_lead to GA4
Type: bug · ICE 576 (I8 C9 E8)
Where (url): https://harbourline.example/
Where (selector): `.wpcf7`
Where (plugin): WPCode snippet "lead-event"
Environment: Chrome desktop; GA4 via gtag.js

Reproduce:
1. Open the homepage and wrap dataLayer.push to record events.
2. Fire the form's success event on the form element (synthetic; nothing is sent).
3. Wait 1.5 s, then read dataLayer and the /g/collect requests.

Expected: generate_lead in dataLayer and a GA4 hit with en=generate_lead.
Actual: No new dataLayer entries. The old snippet listened on .wpcf7-form, which the new theme renamed.
Evidence:
- dom: dataLayer +0 after synthetic success event; snippet selector .wpcf7-form matches 0 elements
- log: WPCode snippet "lead-event" active, last edited before release 4.0

Fix:
1. Listen on document instead of a theme class: document.addEventListener('wpcf7mailsent', …).
2. Keep generate_lead marked as a key event in GA4.
3. Confirm in DebugView with one owner-sent test lead marked "TEST".

Suggested change:

```js
// site-wide, not tied to a theme class
document.addEventListener('wpcf7mailsent', function (e) {
  gtag('event', 'generate_lead', { form_id: e.detail.contactFormId });
});
```

Options considered:
- Track the thank-you page view instead: rejected, because the form shows an inline message and has no thank-you URL.
- Move all tracking to GTM: later, as a bigger change than this hotfix.

Done when: T04 passes and DebugView shows generate_lead for the test lead.
Test: `T04` (form_event) — Form success event → generate_lead (no submit). Run: `QA_ONLY=T04 npx playwright test`
Owner action: Agent can do it in code (theme, plugin code, templates, config in the repo)
Risk: Double counting if GTM also fires on the thank-you URL. Keep a single source for the event.
Pre-mortem: It failed because the snippet only loads on the homepage while the form also sits on /contact/. Load it site-wide and add T04b for /contact/.

### BUG-06 · major · perf · observed

Title: Mobile LCP 4.8 s: hero image is lazy-loaded
Type: bug · ICE 336 (I6 C8 E7)
Where (url): https://harbourline.example/
Where (selector): `.hero img`
Where (file): `theme/template-parts/hero.php`
Environment: PageSpeed Insights mobile, lab

Reproduce:
1. Run PageSpeed Insights on the homepage, mobile, 3 times.
2. Check the LCP element.

Expected: LCP ≤ 2.5 s.
Actual: Median LCP 4.8 s. The LCP element is the hero image, which has loading="lazy".

Suggested change:

```html

     width="1600" height="900" fetchpriority="high" alt="">
```

Test: none automated; verify by hand with the steps above.
Owner action: Agent can do it in code (theme, plugin code, templates, config in the repo)
